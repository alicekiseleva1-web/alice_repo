# Проектирование базы данных

## Назначение

PostgreSQL хранит данные системы поиска животных, поиска дома и помощи приютам. База содержит пользователей, животных, приюты, объявления, фотографии, сообщения и заявки помощи, а также справочники и SQL-функции для работы API.

## Схемы

В базе создаются четыре схемы:

- `dict` — справочные значения;
- `main` — таблицы предметной области и бизнес-логика;
- `api` — функции, вызываемые приложением;
- `auth` — резервная схема, в текущей версии таблиц не содержит.

Пароли не хранятся в отдельной таблице авторизации: хэш пароля находится в поле `main.user.password_hash`.

## Справочники `dict`

| Таблица | Назначение |
|---|---|
| `city` | Города: `city_id`, название и уникальный FIAS ID |
| `gender` | Пол животного |
| `animal_status` | Статусы животного |
| `report_type` | Типы объявлений |
| `report_status` | Статусы объявлений |
| `user_role` | Роли пользователей |
| `user_status` | Статусы пользователей |
| `help_request_status` | Статусы заявок помощи |
| `help_category` | Категории помощи: ID, код, название и пояснение |

API передаёт идентификаторы справочников, например `city_id`, `gender_id` и `report_type_id`, а не текстовые коды.

Таблица `dict.city` содержит поле `fias_id` с ограничением уникальности. Город выбирается из подсказки DaData; повторный выбор города с тем же FIAS ID обновляет существующую запись, а не создаёт дубль. `name` не уникально: разные города могут иметь одинаковые названия. `NULL` в `fias_id` разрешён для старых данных; одинаковое название само по себе не является основанием для удаления записи.

`resolve_city` сначала ищет FIAS ID, затем единственную старую запись без FIAS ID по `lower(btrim(name))`. При одном совпадении присваивает ей FIAS ID; при нескольких требует ручного разбора. При отсутствии совпадений использует `INSERT ... ON CONFLICT (fias_id) DO UPDATE`. Полный справочник городов не загружается: `07` не наполняет города, `08` добавляет одну Москву для примеров.

## Основные таблицы `main`

### Пользователь `main.user`

Хранит имя, фамилию, город, телефон, email, хэш пароля, роль, статус и дату регистрации.

- `city_id` связан с `dict.city`;
- `role_id` связан с `dict.user_role`;
- `user_status_id` связан с `dict.user_status`;
- email и телефон уникальны.

### Животное `main.animal`

Хранит владельца, кличку, породу, пол, возраст, окрас, город, описание, статус и даты создания и изменения статуса.

- `owner_id` связан с `main.user`;
- `gender_id` связан с `dict.gender`;
- `city_id` связан с `dict.city`;
- `animal_status_id` связан с `dict.animal_status`.

### Приют `main.shelter`

Хранит название приюта, город, адрес, контакты, описание и дату создания. `city_id` связан с `dict.city`, а `manager_user_id` — с аккаунтом сотрудника приюта. На один аккаунт может приходиться не более одного приюта.

### Объявление `main.report`

Хранит автора, животное, тип, статус, заголовок, описание, место и даты создания, изменения и закрытия.

- `user_id` связан с `main.user`;
- `animal_id` связан с `main.animal`;
- `report_type_id` связан с `dict.report_type`;
- `report_status_id` связан с `dict.report_status`.

В `dict.report_type` хранятся `lost`, `found`, `help` и `adoption` («Ищет дом»). `help` оставлен для старых объявлений, а текущая страница помощи работает с отдельной таблицей `main.help_request`. Для `adoption` функции списка и карточки возвращают название приюта через связь автора с `main.shelter.manager_user_id`; без такой связи возвращается `null`. Остальные типы не получают пометку о нахождении животного в приюте.

### Фотография `main.photo`

Хранит URL фотографии, животное, необязательное объявление, дату добавления и идентификатор `public_id` Cloudinary, допускающий `NULL`. У старых ссылок идентификатор может отсутствовать. Новые загрузки сохраняют его для последующего удаления файла из облака.

`check_photo_owner`, `save_animal_photo`, `delete_animal_photo` имеют уровни `main` и `api`. Записи меняются только после проверки владельца по переданному ID. Сохранение и удаление блокируют строку животного; лимит двух фотографий для API выдерживается и при одновременных загрузках. Замена сохраняет ID фотографии и связь с объявлением. Облачные вызовы выполняются приложением отдельно от транзакции PostgreSQL.

### Сообщение `main.message`

Хранит объявление, автора сообщения, текст и дату создания.

### Заявка помощи `main.help_request`

Хранит приют, автора, заголовок, описание, категорию (`help_category_id` → `dict.help_category`), статус и даты создания и изменения. Для новых заявок категория обязательна на уровне API и SQL-функций; у старых записей допускается `null` без автоматического выбора категории.

Создание, редактирование и смена статуса проверяют связь пользователя с `main.shelter.manager_user_id`. Публичный список показывает заявки от связанного аккаунта приюта со статусом `open` или `in_progress`. Закрытые доступны при `include_closed=true`. Справочники, выборки и изменения реализованы через пары функций `main.*` / `api.*`.

## Связи между сущностями

Ниже показаны связи предметной области. Часть внешних ключей в текущем DDL допускает `NULL`; обязательность полей определяется ограничениями в `04_create_tables.sql`.

```text
dict.city 1 ─── N main.user
dict.city 1 ─── N main.animal
dict.city 1 ─── N main.shelter

main.user 1 ─── N main.animal
main.user 1 ─── N main.report
main.user 1 ─── N main.message
main.user 1 ─── 0..1 main.shelter

main.animal 1 ─── N main.report
main.animal 1 ─── N main.photo

main.report 1 ─── N main.message
main.report 0..1 ─── N main.photo

main.shelter 1 ─── N main.help_request
main.user 1 ─── N main.help_request
```

## Индексы

Для частых запросов созданы индексы по:

- городу и статусу животного;
- статусу, типу, животному и автору объявления;
- объявлению сообщения;
- животному фотографии;
- приюту, статусу и категории заявки помощи.

Уникальные ограничения автоматически создают индексы, в том числе для FIAS ID, email, телефона и связи приюта с аккаунтом. Отдельный индекс по нормализованному названию города не создаётся.

## SQL-функции

Логика разделена на два уровня:

- функции `main.*` содержат проверки и операции с таблицами;
- функции `api.*` вызываются сервисами FastAPI и передают параметры в `main.*`.

Реализованы функции для:

- регистрации пользователя или сотрудника приюта, проверки учётных данных и получения карточки пользователя;
- создания животного, изменения его статуса, получения карточки и каталога с поиском, фильтром по типу открытого объявления и постраничной загрузкой (`main.get_animals` и `api.get_animals`); проверка через `exists` исключает дубли животных при нескольких объявлениях одного типа;
- создания, получения списка, просмотра и закрытия объявлений, а также изменения статуса автором и вывода его объявлений в профиле;
- создания и получения сообщений;
- добавления, получения, замены и удаления фотографий с проверкой владельца;
- получения справочников категорий и статусов, создания, получения, редактирования и изменения статуса заявок помощи;
- разрешения города по FIAS ID через `main.resolve_city` и `api.resolve_city`. При неоднозначных старых записях без FIAS ID функция возвращает ошибку и не создаёт новый дубль.
- получения и редактирования карточки приюта, привязанного к сотруднику.
- списка собственных животных (`get_user_animals`), редактирования животного владельцем (`update_animal`) и объявления автором (`update_report`). Для каждой есть функция `main.*` и обёртка `api.*`. Обновление блокирует строку, проверяет владельца/автора и справочники; связи, фотографии и статусы остаются прежними.
- изменения личных данных (`update_user_profile`) и смены хэша пароля (`get_password_for_change`, `change_user_password`).

Старая функция `add_photo` сохраняется в SQL, но HTTP-маршрут `POST /photo` вызывает `save_animal_photo`. Ограничения функций не заменяют ограничения для произвольного прямого SQL: лимит двух фотографий, например, не задан отдельным ограничением таблицы.

## Согласованность слоёв

| Операция | Python-сервис | Функция `api.*` и одноимённая `main.*` |
|---|---|---|
| Регистрация | `user_service.register_user` | `register_user` |
| Вход | `user_service.login_user` | `get_user_credentials`; проверка хэша выполняется в Python |
| Личные данные | `user_service.update_user_profile` | `update_user_profile` |
| Пароль | `user_service.change_user_password` | `get_password_for_change`, `change_user_password` |
| Город | `user_service.resolve_city` | `resolve_city` |
| Каталог и свои животные | `animal_service` | `get_animals`, `get_user_animals` |
| Редактирование животного | `animal_service.update_animal` | `update_animal` |
| Объявления и статусы | `report_service` | `get_reports`, `get_report`, `get_user_reports`, `update_report`, `change_report_status` |
| Приют | `shelter_service` | `get_user_shelter`, `update_user_shelter` |
| Фото | `photo_service` | `check_photo_owner`, `save_animal_photo`, `delete_animal_photo`, `get_photos` |
| Сообщения | `message_service` | `create_message`, `get_messages` |
| Помощь | `help_request_service` | `get_help_categories`, `get_help_statuses`, `create_help_request`, `get_help_requests`, `update_help_request`, `change_help_request_status` |

Маршруты и Pydantic-схемы находятся в соответствующих модулях `back/app/routers` и `back/app/schemas`. Изменение состава или порядка возвращаемых SQL-полей требует согласованной проверки сервиса, формирования JSON в роутере и модели ответа.

## Скрипты базы данных

| Файл | Назначение |
|---|---|
| `00_drop_all.sql` | Отдельный разрушительный сценарий сброса: удаление схем проекта и зависимых объектов; не входит в установку |
| `01_create_user.sql` | Создание роли PostgreSQL для учебного окружения |
| `02_create_database.sql` | Создание базы данных `animal_help` |
| `03_create_schemas.sql` | Создание `auth`, `api`, `main`, `dict` через `IF NOT EXISTS`, без удаления существующих объектов |
| `04_create_tables.sql` | Создание таблиц и внешних ключей |
| `05_create_indexes.sql` | Создание индексов |
| `06_create_functions.sql` | Создание SQL-функций предметной области |
| `07_insert_dict.sql` | Начальное заполнение статусов, ролей, типов объявлений, пола животных и категорий помощи |
| `08_test_data.sql` | Необязательные тестовые данные для чистой базы |

Порядок первичной установки описан в [README](../README.md#подготовка-базы-данных). `01`/`02` нужны только для ещё не созданных роли и базы. Затем выполняются `03`–`07` и необязательный `08`. Повторный запуск `03` не удаляет данные, но не обновляет таблицы и функции. Повторный запуск всей последовательности на рабочей базе недопустим.

`00_drop_all.sql` выполняется только при намеренном полном сбросе после резервного копирования. Он удаляет схемы проекта в одной транзакции; `CASCADE` удаляет также зависимые объекты, в том числе из других схем. Отсутствующие схемы пропускаются благодаря `IF EXISTS`. Скрипт не создаёт структуру заново и не восстанавливает данные. Для новой установки после сброса используются `03`–`07` и необязательный `08`.

Основные файлы описывают структуру для чистой установки. Обновление заполненной БД выполняется отдельно с учётом её текущей структуры; автоматизированный механизм миграций отсутствует. Перед обновлением требуется резервное копирование БД.

## Работа с паролями

Приложение хэширует пароль алгоритмом PBKDF2-HMAC-SHA256 до вызова SQL-функции регистрации. В базу передаётся только хэш.

Личные данные меняются через `main.update_user_profile` / `api.update_user_profile` без изменения роли, статуса и пароля. При смене пароля `get_password_for_change` блокирует строку пользователя; приложение проверяет текущий пароль и вызывает `change_user_password` с ожидаемым и новым хэшами в той же транзакции. Открытый пароль в SQL не передаётся.

Тестовые пользователи из `08_test_data.sql` содержат старые условные значения в поле `password_hash`, поэтому они подходят для проверки связей и выборок, но не для входа через текущий маршрут `/login`.
