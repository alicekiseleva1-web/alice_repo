# Проектирование API

## Назначение

API предоставляет доступ к системе поиска животных, поиска для них дома и помощи приютам. Через него клиент регистрирует пользователей, выбирает города, работает с животными, объявлениями, фотографиями, профилями и заявками помощи. Маршруты сообщений реализованы; веб-интерфейс переписки отсутствует.

Контракты API доступны в Swagger и `GET /openapi.json`.

## Технологии и устройство

- Python и FastAPI;
- Pydantic-схемы для проверки входных и выходных данных;
- PostgreSQL;
- `psycopg2` для подключения к базе данных;
- SQL-функции PostgreSQL в схемах `main` и `api`;
- React/Vite как клиентское приложение.

Запрос обрабатывается следующим образом:

1. `app/routers` принимает HTTP-запрос и формирует ответ;
2. `app/schemas` задаёт Pydantic-модели, по которым FastAPI проверяет входные данные и ответы маршрутов с `response_model`;
3. `app/services` выполняет параметризованные вызовы `api.*`, а SQL-обёртки вызывают бизнес-логику `main.*`.

Сервисы DaData и Cloudinary обращаются к внешним API, а не к SQL-функциям. Порядок столбцов SQL-выборки важен: многие роутеры переводят кортежи сервисов в JSON по позициям.

Swagger доступен после запуска сервера по адресу `http://127.0.0.1:8000/docs`.

В режиме разработки CORS разрешён для клиентского приложения `http://localhost:5173`.

## Формат и ошибки

Большинство маршрутов использует JSON. Загрузка и замена файлов используют `multipart/form-data`. FastAPI возвращает `422` при ошибке проверки входных данных. Обработчик в `app/main.py` оставляет только `loc`, `msg`, `type`, не возвращая введённые пароли в поле `input`.

Для отдельных ситуаций API возвращает:

- `400` при бизнес-ошибках, явно обработанных маршрутом: неизвестный справочный ID при редактировании, неверный текущий пароль, нарушение правил фотографии;
- `401` при неверном email или пароле в `/login`;
- `403` при несовпадении переданного ID с владельцем животного, автором объявления или сотрудником приюта в маршрутах, где такая проверка реализована;
- `404` при отсутствии записи в маршрутах с соответствующим обработчиком;
- `409` при занятом email или телефоне в обновлении профиля;
- `502` при обработанной ошибке DaData или загрузки Cloudinary;
- `500` при необработанном исключении, в том числе в маршрутах без перевода бизнес-ошибок в HTTP-коды.

Ошибки `HTTPException` имеют поле `detail`, общий обработчик `500` — поле `error`. Формат ответа зависит от обработчика маршрута. Например, запрет сообщения в закрытом объявлении может возвращаться как `500`, а не `400`.

Вход возвращает только `user_id`; фронтенд сохраняет его в localStorage. Проверки совпадения ID и связи с приютом реализованы, однако серверная аутентификация последующих запросов по токену или сессии отсутствует.

### GET /

Проверяет, что FastAPI-сервер запущен.

```json
{
  "message": "server works"
}
```

### GET /db-test

Проверяет подключение к PostgreSQL и возвращает имя текущей базы данных.

## Пользователи и города

### POST /register

Регистрирует пользователя. Пароль длиной 8–128 символов хэшируется PBKDF2-HMAC-SHA256 на стороне приложения перед сохранением в базе данных.

Для представителя приюта дополнительно передаются `is_shelter: true`, `shelter_name`, `shelter_address`, `shelter_description`. Все три строки должны быть непустыми; максимальная длина — 200, 500 и 1000 символов соответственно. SQL создаёт пользователя и связанный приют. Для обычного пользователя `is_shelter` по умолчанию `false`.

```json
{
  "first_name": "Анна",
  "last_name": "Иванова",
  "city_id": 1,
  "phone": "+79990000001",
  "email": "anna@example.com",
  "password": "password123"
}
```

Ответ:

```json
{
  "user_id": 1
}
```

### POST /login

Проверяет email и пароль пользователя.

```json
{
  "email": "anna@example.com",
  "password": "password123"
}
```

При успешном входе возвращает `user_id`.

### GET /user/{user_id}

Возвращает карточку пользователя: контактные данные, роль, статус, город, количество животных и дату регистрации.

### PATCH /user/{user_id}

Обновляет `first_name`, `last_name`, `phone`, `email`, `city_id`. Все поля обязательны, строки обрезаются по краям; имя/фамилия до 100 символов, телефон 7–20, email до 255. Город выбирается через DaData. Роль, статус, пароль, животные и данные приюта не меняются. Занятый email или телефон возвращает `409`, неизвестный город — `400`, пользователь — `404`. После смены email вход выполняется с новым адресом.

### PATCH /user/{user_id}/password

Принимает `current_password`, `new_password`, `confirm_password`. Новый пароль — 8–128 символов, должен отличаться от текущего и совпадать с повтором. Сервер проверяет старый пароль через PBKDF2, блокирует строку пользователя на время проверки и сохраняет новый хэш в той же транзакции. Неверный текущий пароль — `400`. Пароли и хэши не возвращаются клиенту; ответы валидации не содержат введённых значений. Проверка текущего пароля применяется только к этой операции и не является механизмом аутентификации остальных запросов.

### POST /cities/suggest

Получает подсказки городов через DaData. Ключ DaData хранится только в переменной окружения `DADATA_API_KEY` на сервере.

```json
{
  "query": "Моск"
}
```

Каждая подсказка содержит название города, FIAS ID и отображаемую строку.

### POST /cities/resolve

Находит город по FIAS ID либо добавляет новый город в справочник. В ответе возвращает внутренний `city_id`, который затем передаётся в регистрацию и другие операции API.

```json
{
  "city_name": "Москва",
  "city_fias_id": "0c5b2444-70a0-4932-980c-b4dc0d3f02b5"
}
```

## Животные

### GET /animals

Возвращает каталог всех животных, по одной записи на животное независимо от количества объявлений.

- `query` — необязательный поиск по части клички, породы или названия города без учёта регистра, до 100 символов;
- `limit` — размер страницы от 1 до 100, по умолчанию 24;
- `offset` — смещение от 0, по умолчанию 0.
- `report_type_id` — необязательный ID типа открытого объявления; фильтр применяется до постраничной загрузки. Без него возвращается весь каталог.

Записи отсортированы от новых к старым. Каждый элемент содержит `animal_id`, `animal_name`, `breed`, `gender_id`, `age`, `color`, `description`, `city_id`, `city_name`, `owner_name`, `owner_phone`, `photo_url` и `shelter_name`. Обложка берётся из последней фотографии животного; приют — по связи владельца с `main.shelter.manager_user_id`. Отсутствующие данные возвращаются как `null`.

Страница «Животные» показывает вкладки «Ищут дом» (тип 4), «Пропали» (тип 1), «Найдены» (тип 2), карточки по 24 записи, поиск и окно подробностей. В каждой вкладке животное отображается один раз при наличии открытого объявления соответствующего типа. Закрытые объявления не учитываются. Надпись «Познакомиться» используется только во вкладке «Ищут дом», в остальных — «Подробнее». Все фотографии открытой карточки загружаются через `GET /photo_list/{animal_id}`.

### POST /animals

Создаёт карточку животного.

```json
{
  "owner_id": 1,
  "name": "Барсик",
  "breed": "Метис",
  "gender_id": 1,
  "age": 3,
  "color": "Серый",
  "city_id": 1,
  "description": "Домашний кот"
}
```

Ответ содержит `animal_id`.

### GET /animals/{animal_id}

Возвращает подробную карточку животного, включая город, владельца, телефон владельца и текущий статус.

### PATCH /animals/{animal_id}/status

Изменяет статус животного.

```json
{
  "animal_status_id": 2
}
```

### GET /user/{user_id}/animals

Возвращает все карточки, где `main.animal.owner_id` совпадает с переданным пользователем, включая животных без объявлений. Поля: `animal_id`, `name`, `breed`, `gender_id`, `age`, `color`, `city_id`, `city_name`, `description`. Незаданные поля старых записей могут быть `null`.

### PATCH /animals/{animal_id}

Сохраняет форму редактирования животного из ЛК. Все поля формы обязательны: `user_id`, `name` (до 100 символов), `breed` (до 100), `gender_id`, `age` (целое от 0), `color` (до 100), `city_id`, `description` (до 5000). Город выбирается через существующие подсказки DaData; в обновление передаётся внутренний ID. Владелец, статус, фотографии и связи с объявлениями не изменяются.

SQL проверяет владельца и существование справочных значений. Ответы: `404` — животное не найдено, `403` — переданный пользователь не владелец, `400` — неизвестный город или пол, `422` — неверная форма. Успех возвращает `message`.

Проверка владельца по переданному `user_id` не заменяет аутентификацию: ID поступает от клиента без подтверждения серверной сессией.

## Объявления

### POST /report

Создаёт объявление, связанное с пользователем и животным.

В начальном справочнике `report_type_id`: `1` — пропало (`lost`), `2` — найдено (`found`), `3` — помощь (`help`), `4` — ищет дом (`adoption`). Тип `help` остаётся для совместимости со старыми объявлениями. Новые потребности приюта публикуются отдельно через `/help_request` и `main.help_request`; форма создания обычного объявления предлагает только типы 1, 2 и 4. В другой базе соответствие ID необходимо проверить по справочнику.

```json
{
  "user_id": 1,
  "animal_id": 1,
  "report_type_id": 1,
  "title": "Пропал кот",
  "description": "Убежал вечером",
  "location": "Парк Победы"
}
```

Ответ содержит `report_id`.

### GET /report_list

Возвращает список открытых объявлений. Поддерживает необязательные параметры:

- `report_type_id` — тип объявления;
- `city_id_value` — город;
- `limit_value` — количество записей, по умолчанию 20;
- `offset_value` — смещение, по умолчанию 0.

Каждый элемент содержит `shelter_name`: название приюта автора для типа `adoption`. Для автора без привязанного приюта и для остальных типов поле равно `null`.

### GET /report/{report_id}

Возвращает подробную карточку объявления: данные объявления, животного, автора и города.

`city_id` содержит ID города, а `city_name` — его название из `dict.city` для отображения в интерфейсе. Если название отсутствует, `city_name` равно `null`.

Поле `shelter_name` заполняется по тем же правилам, что в списке. Интерфейс показывает его как «Находится в приюте: …». Название берётся из текущей карточки приюта.

### PATCH /report/{report_id}/close

Закрывает объявление. Тело запроса не требуется.

Маршрут не принимает ID автора и не проверяет принадлежность объявления. Личный кабинет использует `/report/{report_id}/status`.

### GET /user/{user_id}/reports

Возвращает объявления переданного пользователя, включая закрытые. Поля: `report_id`, `animal_id`, `animal_name`, `report_type_id`, `title`, `description`, `location`, `city_id`, `report_status_id`, `report_status_code`, `created_at`, `updated_at`, `closed_at`. Список используется вкладкой «Мои объявления».

### PATCH /report/{report_id}/status

Принимает JSON с `user_id` и `report_status_id`, проверяет автора в SQL и меняет статус на открытый или закрытый. В исходном наполнении это ID 1 и 2. Возвращает `message`. Роутер не переводит исключения SQL в отдельные коды `400`/`403`/`404`, поэтому их перехватывает общий обработчик `500`.

### PATCH /report/{report_id}

Редактирует своё открытое или закрытое объявление. Тело содержит обязательные `user_id`, `report_type_id`, `title` (до 255 символов), `description` (до 5000), `location` (до 1000). Пустые строки и лишние поля отклоняются. SQL проверяет автора по переданному ID и тип объявления. Обновляется `updated_at`; животное, автор, статус, дата закрытия, фотографии и сообщения не меняются.

Ответы: `404` — объявление не найдено, `403` — переданный пользователь не автор, `400` — неизвестный тип, `422` — неверная форма. Успех возвращает `message`. Для редактирования используется список своих объявлений `GET /user/{user_id}/reports`, содержащий и открытые, и закрытые записи.

## Карточка приюта

### GET /user/{user_id}/shelter

Возвращает приют, связанный с `manager_user_id`, либо JSON `null`, если связи нет. Поля: `shelter_id`, `name`, `address`, `description`, `created_at`. Именно наличие этой связи используется интерфейсом помощи приютам.

### PATCH /user/{user_id}/shelter

Принимает `name`, `address`, `description` и возвращает обновлённую карточку приюта. Менять город и контакты приюта эта форма не позволяет. Она также не изменяет личные данные сотрудника.

## Фотографии

### POST /photo/upload

Загрузка JPEG, PNG или WebP до 5 МБ через `multipart/form-data`: обязательные `animal_id`, `user_id`, `file`, необязательный `report_id`. Проверяется владелец животного. На животное допускается не более двух фото; ограничение повторно проверяется SQL под блокировкой строки животного. Сохраняются URL и `public_id` Cloudinary. При ошибке сохранения в БД выполняется попытка удалить только что загруженный файл.

### PUT /animals/{animal_id}/photos/{photo_id}

Заменяет фото: multipart-поля `user_id` и `file`. Сначала загружается новый файл, затем обновляются URL и `public_id` существующей записи. ID фотографии и привязка к объявлению сохраняются. После успешного сохранения выполняется удаление старого файла по сохранённому `public_id`.

### DELETE /animals/{animal_id}/photos/{photo_id}

Удаляет фото животного. Обязательный query-параметр `user_id`; SQL проверяет владельца. Сначала удаляется запись в БД, затем файл Cloudinary, если известен `public_id`. Если очистка облака не удалась, операция возвращает успех с `warning`: фото уже удалено с сайта, но файл может остаться в облаке. Старые фото без `public_id` удаляются только с сайта — идентификатор не вычисляется из URL.

Добавление, замена и удаление доступны в ЛК → «Мои животные» → «Фотографии». Перед сохранением показывается предпросмотр; удаление требует подтверждения.

### POST /photo

Добавляет URL фотографии животного. Фотография может быть дополнительно связана с объявлением.

```json
{
  "user_id": 1,
  "animal_id": 1,
  "report_id": 1,
  "url": "https://example.com/cat.jpg"
}
```

Ответ содержит `photo_id`.

### GET /photo_list/{animal_id}

Возвращает список фотографий выбранного животного.

## Заявки помощи приютам

### GET /help_categories и GET /help_request_statuses

Возвращают справочники категорий (`help_category_id`, `name`, `description`) и статусов (`help_request_status_id`, `code`, `name`). Категории: «Помочь делом», «Поддержать финансово», «Передать необходимое». Клиент получает ID из API и передаёт их при создании, редактировании и фильтрации.

### POST /help_request

Создаёт заявку от имени своего приюта. SQL требует совпадения переданного `user_id` с `main.shelter.manager_user_id`. Категория обязательна, начальный статус — `open`.

```json
{
  "shelter_id": 1,
  "user_id": 2,
  "help_category_id": 3,
  "title": "Нужен корм",
  "description": "Требуется сухой корм для собак"
}
```

Ответ содержит `request_id`.

### GET /help_request_list

Возвращает заявки, опубликованные связанным с приютом аккаунтом. По умолчанию показывает только `open` и `in_progress`. Параметры: `shelter_id`, `help_request_status_id`, `help_category_id`, `include_closed` (по умолчанию false), `limit` (1–100, по умолчанию 24), `offset` (от 0). Фильтрация выполняется до постраничной загрузки.

Ответ включает название категории и приюта, город, адрес, телефон, email, статус и даты. Телефон/email берутся из приюта, при их отсутствии — из аккаунта сотрудника. Старые заявки без категории возвращают `null`; категория не назначается автоматически. Старые записи, созданные не связанным с приютом пользователем, не публикуются в ленте, но из БД не удаляются.

### PATCH /help_request/{request_id}

Редактирует заголовок, описание и категорию заявки своего приюта. JSON содержит `user_id`, `title`, `description`, `help_category_id`. Статус остаётся прежним.

### PATCH /help_request/{request_id}/status

Изменяет статус заявки своего приюта. `user_id` и ID статуса передаются в JSON. При передаче ID обычного пользователя или сотрудника другого приюта возвращается `403`. Отсутствующая заявка — `404`, неизвестный статус — `400`, неверная структура запроса — `422`.

Пример:

```json
{
  "user_id": 2,
  "help_request_status_id": 2
}
```

Страница `#help` содержит категории, карточки с контактами, публикацию, редактирование и управление статусами. У сотрудника есть фильтр «Заявки моего приюта, включая закрытые». Статус «Открыта» в карточках не выводится, но остаётся в данных. Переводы через сайт не принимаются. `include_closed=true` сам по себе не ограничен аутентификацией, даже если интерфейс показывает этот фильтр сотруднику. Проверка связи аккаунта с приютом не заменяет серверную аутентификацию: клиент передаёт `user_id` без подтверждения сессией.

## Границы реализации

Административный интерфейс и серверная авторизация на основе сессий или токенов не реализованы. Доступны личный кабинет, редактирование личных данных, смена пароля, управление фотографиями, животными и объявлениями пользователя, поиск животных и API карточки приюта.
